# 实验4 静态分析基本方案

## 一、实验要求

依据 `课程资料/整体上机课程安排.pptx`第5页“上机4：静态分析”，本实验需要：

1. 了解阿里 Java 编程规范，使用 Alibaba Java Coding Guidelines 检测 Java 代码。
2. 使用 FindBugs 分析 Java 代码并检测缺陷。
3. 对检测结果进行人工核查，统计误报率。
4. 修复人工确认的缺陷，修复后重新检查。

2026年10月8日已完成P3C最终复查、FindBugs3.0.1兼容副本全范围分析、8项告警核查、7项修正及同范围复查，96项单元测试回归通过。FindBugs原版直接运行仍不兼容Java17，兼容方式和局限见[实验报告](实验4成果/实验4实验报告.md)。

## 二、测试对象与范围

测试对象为 Keyboard MES 后端，工程位于 `program/code/backend`，使用 Java 17 和 Maven。首轮扫描覆盖 `src/main/java` 中的业务代码；重点核查工单、生产任务、报工、质检、返修与追溯服务，以及权限校验和异常处理。测试源码可作为理解业务和后续验证的辅助材料，统计时与正式业务代码分开。

实验1质量需求、实验2业务用例和实验3单元测试可用于判断告警是否影响实际业务。历史测试通过不能代替本实验的人工核查或修复后验证。

## 四、实施步骤

1. **建立扫描基线**：记录源码版本、扫描范围、工具版本和规则配置，保留初次扫描原始结果。
2. **进行两类扫描**：分别输出规约检查和缺陷检测结果，截图保留工具界面、代表性告警和汇总信息。
3. **人工核查**：逐项查看源码与调用关系，将告警判定为确认问题、误报或待核查，说明依据。规约不符合与业务缺陷分别统计；同一工具的重复告警按约定去重。
4. **修复确认问题**：优先处理可能导致错误数据、异常或权限问题的缺陷，每项修复关联原告警编号；不批量自动修改未经核查的告警。
5. **复查与验证**：使用相同范围和规则重新扫描，对比告警变化。进入实际修复阶段时，结合相关单元测试验证行为；未执行的验证如实注明。
6. **整理报告**：说明检测方法、典型核查过程、误报率、修复效果和局限，以实际截图与数据支持结论。

## 五、记录与统计口径

每项记录包含：编号、工具、规则或缺陷类型、文件和行号、告警说明、人工判定、判定依据、修复情况、复查结果及证据位置。

误报率按各工具分别计算：**误报数 ÷ 已完成核查的告警数 × 100%**。同时报告告警总数、已核查数和待核查数；全部完成核查时，分母即该工具的告警总数。没有已核查告警时标为“不适用”。两类工具结果不直接合并计算误报率；规约告警被确认不符合时，不能仅因不影响运行而计作误报。

## 六、文件组织与预期成果

本实验在 `4/` 下工作，继续复用现有后端工程，不复制一份源码。

- `实验4方案.md`：本方案。
- `实验4成果/`：实际开展后保存报告正文、Word 提交件和人工核查明细。
- `实验4成果/证据/`：必要截图和扫描结果；提交前检查敏感信息。

临时脚本、下载缓存和排版预览放系统临时目录，编译产物保留在被忽略的 `backend/target` 中。工具安装包不默认纳入仓库。

完成标准：两类扫描有真实记录；告警有明确核查状态及统计口径；确认缺陷有修复和复查依据；报告与证据一致。工具不兼容、待核查或未完成验证的部分应明确说明。
