# 静态分析复现说明

## 工具和范围

- 主项目以JDK 17编译。本次使用Maven 3.9.11。
- [阿里P3C官方规则](https://github.com/alibaba/p3c/tree/master/p3c-pmd)：`com.alibaba.p3c:p3c-pmd:2.1.1`。
- Java17源码解析使用`net.sourceforge.pmd:pmd-java:6.55.0`。
- [FindBugs原版](https://findbugs.sourceforge.net/)：`com.google.code.findbugs:findbugs:3.0.1`。必须与PMD依赖分开，使用FindBugs原配ASM5依赖。
- 有限FindBugs分析运行环境为[Temurin8官方JRE](https://github.com/adoptium/temurin8-binaries/releases/download/jdk8u504-b01/OpenJDK8U-jre_x64_windows_hotspot_8u504b01.zip)。SHA256为`82e2cdc6693737c5998445b31f69668fa0da77c7705121053f6508ac84961123`。

扫描覆盖`program/code/backend/src/main/java`下72个文件。启用的P3C规则集为`ali-exception`、`ali-comment`、`ali-other`、`ali-naming`、`ali-flowcontrol`、`ali-orm`、`ali-constant`、`ali-set`、`ali-oop`、`ali-concurrent`，资源路径均为`rulesets/java/<名称>.xml`。

## 执行方法

将所需工具及依赖下载到仓库外的工具目录。P3C的`messages.xml`和`messages_en.xml`需另存到资源覆盖目录，在XML声明后补上`<!DOCTYPE properties SYSTEM "http://java.sun.com/dtd/properties.dtd">`，该目录放在扫描类路径最前面。只修改消息XML，不改规则实现。

```text
java -Dfile.encoding=UTF-8 -cp "消息覆盖目录;PMD依赖目录/*" net.sourceforge.pmd.PMD -d "源码目录" -R "十个规则XML路径以逗号分隔" -f xml -r "输出.xml" -language java -version 17 --no-cache
```

早期原版FindBugs对项目Java17编译产物的尝试没有形成有效全项目结果，兼容性错误摘录已保存。有限分析的14个类明确列于`扫描范围.csv`，仅来自entity、dto和util。其未改动的源文件通过JDK17的javac使用`-source 8 -target 8`另编译到临时目录，并以项目依赖为编译类路径。编译会提示未设置Java8引导类路径，该副本不是Java8运行兼容性证明。

```text
JRE8/java -cp "FindBugs原配依赖目录/*" edu.umd.cs.findbugs.FindBugs2 -effort:max -low -xml:withMessages -output "输出.xml" "临时分析类目录"
```

修改后回归在后端目录执行`mvn -o -DforkCount=0 -Djacoco.skip=true test`。本次已执行的最终命令为`mvn -o -DforkCount=0 test`，96项通过；其中JaCoCo输出含旧执行数据不匹配提示，故只保留测试结果，不使用该次覆盖率。成员正常环境可使用标准`mvn test`。

## 证据口径

原始扫描XML中的工作区和临时目录路径已替换为占位符，告警、计数及分析时间保留。回归明细来自最终Surefire XML；历史实验3覆盖率成果未改动。早期14个类的结果仅作为历史证据；当前72个源文件的全范围结果见findbugs-full-before.xml、findbugs-full-after.xml和FindBugs告警核查明细.csv。

## 2026年10月8日全范围兼容分析

本次没有替换为SpotBugs。原版发行包仍不能直接解析Java17；正式使用的是明确标注的FindBugs3.0.1兼容副本，不能称为原版直接运行成功。

1. 用项目JDK17和Maven编译实际源码，生成`backend/target/classes`。本次72个源文件对应73个类，包含一个嵌套类。
2. 在仓库外准备原版FindBugs3.0.1及其依赖、ASM9.7的asm/asm-tree/asm-commons、JRE8和项目实际依赖清单。
3. 执行`python prepare_findbugs_compat.py 原版findbugs.jar JDK17目录 临时输出目录`。脚本只修改13处ASM访问器API整数参数（327680改为589824）并删除JAR清单中的旧相对依赖入口，不修改告警判定逻辑。同时从本机JDK17的java.base和java.rmi模块提取辅助平台类，不改变应用字节码。
4. 将上述两个平台类JAR和Maven项目依赖路径逐行写入辅助类路径文件。FindBugs的`-auxclasspathFromFile`要求每行一个条目，不能写成一整行分号列表。
5. 运行时类路径顺序为ASM9.7三个JAR、生成的findbugs-api9.jar、原配其余依赖。排除原版findbugs.jar与ASM5；BCEL仍使用bcel-findbugs6.0。由JRE8启动以下命令：

```text
java -cp "上述运行类路径" edu.umd.cs.findbugs.FindBugs2 -effort:max -low -auxclasspathFromFile "逐行依赖清单.txt" -xml:withMessages -output "扫描.xml" "backend/target/classes"
```

初次8项告警，7项确认问题修正后复查1项；两次均73个类、分析错误0、缺失类0。剩余项来自try-with-resources的隐式关闭检查，未通过排除规则隐藏。兼容副本没有官方Java17支持保证，旧检测器对新语法的覆盖能力仍有限。

最终回归命令为`mvn -o -DforkCount=0 -Djacoco.skip=true test`（PowerShell中应将每个带点的-D参数整体加引号）。2026年10月8日96项测试全部通过。本次没有重新形成覆盖率结论。最终P3C复查为0项告警；日志仍有历史同类DFA迭代提示，XML无处理错误。
