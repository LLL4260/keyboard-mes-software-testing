## 1.3 系统应用

需求追踪覆盖率为52/52=100%，执行完成率为59/76=77.6%。17项阻塞使整体退出条件尚未满足；59项已完成用例通过并不代表整个系统测试通过。

TestLink把需求、执行状态和缺陷回归联系起来，适合用于后续版本比较。补测时应明确执行环境与构建，满足专项条件后再更新状态，保留历史记录。

## 单元测试工具（JUnit+Mockito+Jacoco）

## 2.1 设计思路

单元测试围绕核心业务规则设计正常、边界和异常输入。使用JUnit组织测试，使用Mockito隔离Mapper等外部依赖，通过可控制的返回值与异常检查服务行为；JaCoCo用于观察代码覆盖情况。

重点覆盖工单与任务流转、报工数量、质检处置、返修复检和SN追溯。对validateReportQuantity进行基本路径分析，列出6条独立路径，并将输入条件、预期结果与对应测试联系起来。

## 2.2 实现过程

测试采用准备数据、执行方法、验证返回或异常的结构，必要时检查依赖调用及状态更新。既有结果包含19个测试类、96项测试，失败、错误和跳过均为0。

六个核心服务的JaCoCo行覆盖为460/463，分支覆盖为235/256。2026年10月8日代码整改后，96项测试再次全部通过；该次回归未重新采集覆盖率，覆盖统计仍使用实验3的留档数据。

## 2.3 系统应用

核心服务行覆盖率99.4%、分支覆盖率91.8%，达到既定85%和80%的目标。JaCoCo行覆盖作为语句覆盖的近似指标，不与分支覆盖混用。

覆盖目标只针对所统计的六个核心服务。报表服务及其他扩展服务仍存在测试缺口，后续应补充业务边界与异常处理用例；高覆盖率也不能替代断言对业务结果的检查。

## 静态测试工具（Alibaba Java Coding Guidelines、Spotbugs）

## 3.1 设计思路

静态测试从编码规范与潜在缺陷两个方面开展。Alibaba Java Coding Guidelines检查注释、命名、集合、异常及并发等规则；SpotBugs检查编译类中的潜在问题。

扫描范围为后端正式代码，测试源码、前端、小程序与依赖库不计入正式源码范围。告警需结合源码和框架使用方式核查，区分确认缺陷、误报及保留的设计风险。

## 3.2 实现过程

2026年10月11日使用官方SpotBugs 4.10.4分析73个Java 17编译类，初查与复查均为15项告警，分析错误和缺失类均为0。阿里官方P3C规则2.1.1配合PMD 6.55.0检查72个源文件，结果为0项。

SpotBugs告警均为EI_EXPOSE_REP2。核查后，13项属于容器管理的拦截器或Mapper代理在当前框架场景下的误报；2项涉及共享ObjectMapper和Redis模板，保留为配置可变性风险。源码未因这些告警修改，复查仍为15项。

## 3.3 系统应用

误报率按误报数除以已核查告警数计算，为13/15=86.7%，仅适用于本次告警；阿里规约0项告警时误报率不适用。共享组件应在初始化时完成配置，运行期间避免随意重新配置。

此前阿里规约发现的208项不符合已完成修正，本次同范围检查继续保持0项。静态分析为代码维护提供依据，但检测范围和规则有限，需与单元测试及系统测试结合。

## 接口测试工具（Postman）

## 4.1 设计思路

接口测试覆盖工单、生产任务和生产报表三类服务，并补充健康检查、登录、退出和异常响应。测试集合按业务顺序组织，兼顾HTTP状态、业务码、字段结构和会话状态。

登录请求提取会话标识，工单列表提取编号供详情查询使用。这样可以减少对固定数据编号的依赖，同时验证接口之间的变量传递。

## 4.2 实现过程

Postman集合通过Newman 6.2.1执行，使用隔离数据库和独立Redis实例。测试查询既有业务数据，并创建和结束登录会话，没有新增工单、报工或质检记录。

首次执行时质量趋势断言使用了错误字段，核对接口后改为trendData并检查7天趋势；修正后完整集合共10个请求、20项断言全部通过。不存在工单和退出后查询分别按业务码500与401判断，即使HTTP 200也不按正常成功响应处理。

## 4.3 系统应用

已有结果说明所测三类查询与会话操作在当前数据和管理员测试会话下符合预期。动态变量和业务断言使集合可以用于后续接口回归。

测试尚未覆盖业务写入、全部角色权限及所有接口组合。后续可增加工单状态变化和不同角色的用例，写入测试应安排独立数据与清理步骤。

## 性能测试工具（JMeter + Badboy）

## 5.1 设计思路

性能测试采用单用户基线和十用户查询负载，观察错误率、平均响应时间、P95和吞吐量。每个线程先登录，循环访问工单、任务和生产概览，再退出。

业务查询同时检查HTTP与业务响应，每次查询前等待300毫秒。Badboy用于录制公共只读请求并导出JMX，业务负载与录制流程验证分别统计。

## 5.2 实现过程

JMeter 5.6.3以非图形模式执行。单用户场景循环10次，共32个请求；十用户场景每线程循环20次，共620个请求，两组共652个请求均无失败。

单用户全部请求平均响应10.19毫秒、P95为18毫秒、吞吐量3.01次/秒；十用户全部请求平均响应4.95毫秒、P95为9毫秒、吞吐量26.91次/秒。Badboy 2.2.5另行录制4个只读请求，原生脚本、原始JMX和补充断言JMX的回放失败数均为0。

## 5.3 系统应用

本机短时查询负载下，所测请求与业务断言均通过。十用户场景较低的平均响应可能受缓存预热和请求组合影响，不能解释为并发越高性能越好。

以上结果不代表长期稳定性、写入吞吐或生产容量。后续应依据明确性能需求扩展并发量、持续时间和业务组合，同时保留响应断言与资源监测。
